# 품질과 안전

[English](QUALITY-AND-SAFETY.md)

이 문서는 PCssak Jamak이 지향하는 안전 구조와 공개 전에 필요한 검증 근거를 설명합니다.
오류가 없거나 AI 결과가 정확하다는 보증서가 아니라 엔지니어링 기준입니다.

## 로컬 자막 작업 흐름

Jamak은 사람이 확인할 수 있는 다음 로컬 순서를 중심으로 설계합니다.

1. 사용자가 지원 미디어나 자막 파일을 가져옵니다.
2. 선택한 로컬 엔진이 전사·번역 후보를 만듭니다.
3. 사용자가 자막 문구·시간·언어·스타일과 미리보기를 검수합니다.
4. 사용자가 내보내기나 번인을 명시적으로 시작한 뒤에만 새 자막·영상 결과를 씁니다.
5. 중요한 결과는 실제 재생기나 납품 흐름에서 다시 열어 확인합니다.

AI 결과는 언제나 사람 검수 대상입니다. 제품 문구·화면 이름·모델 크기만으로 전사·번역이
완전하고 정확하며 합법적이고 접근 가능하거나 중요한 용도에 적합하다고 판단하면 안 됩니다.

## 원본과 출력 안전

- 미리보기·전사·번역·편집만으로 원본 미디어와 가져온 자막을 바꾸지 않아야 합니다.
- 내보내기·번인 대상은 명시적이어야 합니다. 기존 출력, 바뀐 경로, 저장 공간 부족, 권한 실패,
  파일 잠금이나 외부 변경은 조용한 덮어쓰기보다 분명한 거부·확인으로 처리해야 합니다.
- 임시·부분 파일은 완료 결과와 구분되어야 하며 성공한 내보내기로 표시하면 안 됩니다.
- 실행 취소·다시 실행·복구 세션·원자적 쓰기는 흔한 실패 위험을 낮추지만 별도 백업을
  대신하지 않습니다.
- 미리보기가 성공해도 모든 재생기·글꼴·코덱·플랫폼·해상도에서 최종 결과가 똑같이 보인다고
  증명되지는 않습니다.

## 관리형 외부 구성요소

선택형 엔진·모델은 사용자가 선택한 뒤에만 내려받습니다. 승인 패키지마다 고정 상위 출처,
예상 압축 형식, 고정 SHA-256, 압축 해제 허용 목록, 저장 범위와 실행 파일 절대 경로를
관리합니다. 해시 불일치, 예상하지 않은 항목, 미완료 다운로드나 안전하지 않은 경로는 검증
우회가 아니라 실패 안전 상태가 되어야 합니다.

v0.1.1은 FFmpeg를 동봉·미러링하지 않고 문서에 표시된 BtbN 릴리스의 선택 GPL 빌드를 직접
받습니다. whisper.cpp, llama.cpp, 모델 가중치, CUDA 런타임, WebView2와 Visual C++ 런타임은
각 상위 라이선스·보안 수명주기·호환성 한계를 따릅니다.

## 개인정보 경계

- 핵심 작업 중 미디어·자막·프롬프트·전사·번역·복구 데이터·생성 결과는 사용자 PC에
  머뭅니다.
- 공개 무료 얼리액세스에는 PCSSAK 계정, 광고, 텔레메트리, 사용량 분석, 추적 SDK와 자동
  오류 업로드가 없습니다.
- 제한된 네트워크 예외는 고정 업데이트 확인·사용자 승인 업데이트, 사용자가 선택한 구성요소
  전달, 필요한 WebView2 전달과 사용자가 직접 연 링크·메시지입니다.
- 공개 제보는 로컬이 아닙니다. 이슈 양식과 지원 안내는 개인 경로·미디어 내용·자막 문구·고객
  자료·자격증명·라이선스 키·회사 비밀 제거를 요구합니다.

## 설치기와 업데이트 무결성

릴리스 절차에는 다음이 필요합니다.

- 프런트엔드·Tauri·Rust·릴리스 노트·태그·메타데이터의 앱 버전 일치
- 정확한 빌드의 깨끗하고 재현 가능한 소스·잠금 파일 상태 기록
- 최종 EULA와 최초 설치 언어 흐름을 포함한 현재 사용자용 다국어 NSIS 설치기
- 정확한 NSIS 업데이트 자산을 대상으로 생성한 필수 Tauri 서명
- 최종 자산에서 만든 `latest.json`, CycloneDX SBOM, 릴리스 노트와 `SHA256SUMS.txt`
- 명시적 자산 허용 목록과 개인키·비밀번호·토큰·로그·테스트 미디어·개발자 경로·예상 밖
  바이너리·오래된 빌드 출력 거부
- 홈페이지 다운로드를 열기 전 독립적인 재다운로드와 해시 비교

Tauri 서명은 앱 내부 업데이트 경로를 보호하며 Windows Authenticode가 아닙니다.
Authenticode를 적용하기 전에는 Tauri 서명과 SHA-256이 맞아도 Windows가 설치기를 알 수 없는
게시자로 표시할 수 있습니다.

고정 홈페이지 엔드포인트는 공개 v0.1.1 설치기·서명·메타데이터·해시·익명 다운로드를 독립
검증할 때까지 `204 No Content`를 유지합니다. 이 검증 뒤 출시 소유자가 명시적으로 승인한 제한
실운영 시험에서는 설치된 v0.1.0 앱에 `200 OK`를 반환해 실제 업그레이드를 시험할 수 있습니다.
다운로드·서명 검증·설치·재시작·표시 버전이 모두 성공하기 전까지 종단 결과는 `NOT_RUN`이며,
시험 실패 시 즉시 `204`로 되돌립니다.

## 검증 계층

공개하는 정확한 릴리스에 대해 다음 결과를 기록해야 합니다.

- 프런트엔드 타입 검사·프로덕션 빌드, Rust 포맷·린트·단위·통합 테스트
- 자막 파싱·시간 경계·분할·병합·편집 기록·검색·형식 변환·스타일·카라오케·미리보기·
  내보내기·복구·안전 출력 회귀 테스트
- 구성요소 다운로드 중단·이어받기·SHA-256 불일치·압축 경로 이탈·저장 한계·제거·CPU와
  지원 CUDA 경로 검증
- 지원 앱·설치 언어의 번역 완전성과 자리표시자 일치
- 문서화한 Windows 에디션에서 깨끗한 설치·최초 실행·복구 설치·업데이트·제거·앱 데이터
  선택 확인
- 릴리스 노트에서 주장하는 범위만큼 실제 x64 Windows 10 22H2와 현재 지원 중인 Windows 11
  Home·Pro 확인
- Defender와 현재 보안 제품 검사, SmartScreen 동작, 미서명 게시자 경고, 오탐 제보와 보안
  기능을 끄라고 안내하지 않는지 확인
- 최종 의존성 인벤토리, 전체 제3자 고지, 해당하는 원본 소스 제공 의무, SBOM 대조와 목표
  배포 지역 법률 검토

자동 테스트 통과만으로 설치 앱·실제 미디어·접근성·현지화·보안·라이선스·업그레이드 검토를
대신할 수 없습니다. 미지원·미완료 조합은 릴리스 노트에 그대로 표시해야 합니다.

출시 소유자가 깨끗한 Windows 설치 후 설치된 `jamak.exe` SHA-256 대조를 실행하지 않기로
결정하면 릴리스 노트에 `NOT_RUN: clean-windows-install-and-sha256`을 정확한 독립 한 줄로
기록해야 합니다. 이는 미실행 기록이지 통과나 Windows 호환성 주장이 아닙니다. 실제 exe/DLL
인벤토리와 원본 해시·PE·Authenticode 상태·Tauri 서명·병합 SBOM·제3자 고지·6자산 허용
목록은 계속 필수입니다. 국가별 위험이나 H.264/AVC 특허 위험의 출시 소유자 수용도 법률
적합성 승인이 아닙니다.
